# Database Compatibility: SQLite vs. PostgreSQL

**Scope:** what was actually checked, what was found, and what remains
unverified. **No live PostgreSQL server was available in this
development environment** (confirmed: a connection attempt to
`127.0.0.1:5432` timed out, and no `DATABASE_URL` pointing at a running
Postgres instance was configured). This document does **not** claim
live-tested parity between SQLite and PostgreSQL — it reports what was
verified by compiling this project's actual DDL against both dialects
(via SQLAlchemy's dialect-aware `CreateTable(...).compile(dialect=...)`,
with `psycopg2` installed and available as the driver), and what still
needs a real server to confirm.

## A real divergence found and fixed, not just noted

Compiling `StancePrediction`'s table against both dialects (before any
fix) showed:

```
-- SQLite
label VARCHAR(7)

-- PostgreSQL
label stancelabel   -- a native CREATE TYPE ... AS ENUM
```

SQLAlchemy's default behavior for a Python `enum.Enum` column is a plain
`VARCHAR` + `CHECK` constraint on SQLite, but a **native PostgreSQL ENUM
type** on PostgreSQL. This is a real, consequential difference: adding a
new value to a native PG enum type later requires `ALTER TYPE ... ADD
VALUE` (which, in older PostgreSQL versions, cannot run inside the same
transaction as other DDL) — a materially different, more operationally
fragile migration path than SQLite's plain column-constraint change.

**Fix:** `backend/app/models/base.py::str_enum()` now passes
`native_enum=False` explicitly. Re-compiling after the fix:

```
-- SQLite
label VARCHAR(7)

-- PostgreSQL
label VARCHAR(7)
```

Identical on both dialects now — confirmed by direct compilation, not
assumed. Every enum column in this schema (`StanceLabel`,
`ExclusionCode`, `PredictionSource`, `ModelComponent`, `SummaryMethod`,
`DocumentProcessingStatus`) goes through this same helper, so the fix is
schema-wide, not per-column.

## Other areas checked (via DDL compilation, both dialects)

| Area | Finding |
|---|---|
| **Constraints** (`CHECK`, including the label/exclusion-code mutual-exclusivity and model-version-required constraints) | Compile identically on both dialects — confirmed by direct comparison of the compiled `CREATE TABLE` text. |
| **Unique constraints** | Identical syntax/semantics on both (`UNIQUE (...)`). |
| **Indexes** | `ix_comments_normalized_text_hash` (and other FK-backed indexes) generate consistently; Alembic's autogenerate detected and rendered them the same way regardless of which dialect the detection ran against. |
| **JSON fields** (`ConcernGroup.hyperparameters`, `ModelVersion.config`) | The generic SQLAlchemy `JSON` type compiles to a plain `JSON` column on both dialects. **Caveat:** this project never performs a JSON-path query (e.g. `hyperparameters->>'key'`) — if that's ever added, the query syntax is NOT portable between SQLite's `json_extract()` and PostgreSQL's `->`/`->>` operators, and would need dialect-specific handling at that point. Simple whole-value store/retrieve (everything this project does today) works identically. |
| **Auto-incrementing primary keys** | SQLAlchemy renders `INTEGER` (with `AUTOINCREMENT` semantics via SQLite's rowid) vs. `SERIAL` on PostgreSQL automatically — no model code difference required. |
| **Timestamps** (`DateTime(timezone=True)`) | Compiles to `DATETIME` on SQLite and `TIMESTAMP WITH TIME ZONE` on PostgreSQL. **Real behavioral difference, documented rather than hidden:** SQLite does not actually enforce or store timezone information at the storage engine level (values are stored as ISO-8601-ish text); PostgreSQL's `TIMESTAMPTZ` genuinely normalizes and stores timezone-aware values. This project's own code only ever constructs these values via `models/base.py::utcnow()` (always UTC, always timezone-aware in Python), so behavior is consistent in practice — but this relies on application discipline on SQLite, not a storage-level guarantee the way it is on PostgreSQL. |
| **Pagination** (`services/pagination.py`) | Built on plain SQLAlchemy `select().limit().offset()` — standard SQL, dialect-agnostic; no dialect-specific pagination code exists or is needed. |
| **Transactions** (ORM session begin/commit/rollback) | SQLAlchemy's ORM session API is dialect-agnostic for this project's usage pattern (no raw dialect-specific transaction control is used anywhere in `backend/app/`). |

## Migration compatibility (Alembic)

- Autogenerated migrations (`backend/migrations/versions/`) render
  portable `sa.*` types (`sa.Enum(...)`, `sa.JSON()`, `sa.DateTime(timezone=True)`,
  etc.), not dialect-specific literals — the same migration file runs
  against either backend; SQLAlchemy's dialect layer handles the
  translation at execution time.
- **Verified by direct testing** (SQLite, this environment — see
  `docs/backend/MIGRATIONS_GUIDE.md`): `alembic upgrade head`, insert
  data, `alembic downgrade base`, re-`upgrade head` — all succeed, and a
  second, additive migration (adding `PolicyDocument.description`) was
  used to confirm that existing rows' other columns survive an
  upgrade-then-downgrade cycle intact.
- **Not verified**: the same sequence against a live PostgreSQL server
  (none available here). Given the DDL-compilation checks above show
  identical rendered SQL for every type actually used in this schema, the
  same migrations are expected to behave the same way on PostgreSQL —
  but "expected, based on compiled DDL" is explicitly weaker evidence
  than "observed against a running server," and this document says so
  rather than quietly upgrading that expectation into a claim.

## How to actually verify against PostgreSQL when a server is available

```
# with a running PostgreSQL instance, e.g. via Docker:
#   docker run --rm -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:16
export DATABASE_URL=postgresql://postgres:dev@localhost:5432/policylens
alembic upgrade head
# ... run the same insert/upgrade/downgrade/re-upgrade sequence from
# MIGRATIONS_GUIDE.md, and the full test suite (tests/ currently runs
# against SQLite only, per tests/conftest.py's db_session fixture) ...
```

This project deliberately does not assume that sequence would pass
unverified — it's the concrete next step for whoever has PostgreSQL
available, not a claim made in its absence.
